# Design Rationale

이 문서는 "왜 이렇게 설계·판단했는지"를 정리합니다. 이 프로젝트의 핵심은 A* 구현이 아니라, 측정 조건을 통제하고 단계별 측정으로 최적화를 판단한 과정입니다. 각 항목은 문제 상황 / 선택한 방식 / 대안 / 선택 이유 / 절충 / 검증 방법 순으로 적습니다. 코드 흐름의 상세는 `docs/Code_Flow.md`, 측정 결과는 `docs/Test_Report.md`를 참고하세요.

---

## 1. 왜 BFS로 경로 존재를 먼저 검증했는가

- 문제 상황: 랜덤 맵에서는 시작→도착 경로가 아예 없는 경우가 생긴다. 그런 맵에서 A*는 격자를 거의 다 탐색하는 최악 케이스가 된다.
- 선택한 방식: A*를 측정하기 전에 BFS로 경로 존재를 확인하고, 없으면 그 맵을 버리고 새로 만든다.
- 대안: 경로 없는 케이스를 그대로 측정에 포함, A*가 실패할 때까지 두기.
- 선택 이유: 경로 없는 케이스가 표본에 섞이면 A*의 탐색량이 튀어 평균이 왜곡된다. A* 자체의 최적화 효과를 공정하게 보려면 경로가 존재하는 케이스만 측정해야 한다. 또한 측정 프로파일러는 BFS 통과 이후에 시작되므로 BFS 시간은 A* 측정에 포함되지 않는다.
- 감수한 점: 반복마다 BFS 1회 비용이 추가된다(측정 구간 밖).
- 검증 방법: 경로 있는 케이스만 5만 회 측정.
- 관련 코드 흐름: BFS ValidateGoal, A* Search.
- 관련 테스트 결과: 5만 회 반복 측정.
- 확인 필요: 없음(코드 확인).

---

## 2. 왜 5만 회 반복 측정했는가

- 문제 상황: 랜덤 맵·시작·도착의 분산이 커서 단일 실행 시간은 크게 흔들린다.
- 선택한 방식: 5만 회를 반복 측정하고, 극단값을 제외한 평균으로 비교한다.
- 대안: 소수 회 측정.
- 선택 이유: 충분한 반복으로 평균 처리시간을 안정화해야, 최적화 전후 비교의 신뢰도가 확보된다.
- 감수한 점: 총 측정 시간이 늘어난다.
- 검증 방법: 결과 파일의 호출 수가 5만인지 확인(측정 결과 Call=50000).
- 관련 코드 흐름: 측정/프로파일링.
- 관련 테스트 결과: `docs/Test_Report.md`.
- 확인 필요: 없음(코드 확인).

## 3. 왜 휴리스틱을 변경했는가

- 문제 상황: 이동 방식과 맞지 않는 휴리스틱은 탐색량을 늘릴 수 있다.
- 선택한 방식: 8방향 이동(직선 1, 대각 1.5)에 맞는 옥타일 형태의 휴리스틱으로 바꾸고, 제곱근을 제거한다.
- 대안: 유클리드 거리(제곱근 포함)를 유지.
- 선택 이유: 8방향 격자에서는 대각 이동을 반영한 휴리스틱이 실제 비용에 더 가까워 탐색 노드 수를 줄인다. 제곱근을 없애면 노드마다의 계산 비용도 줄어든다. 탐색 노드 수와 계산 비용을 함께 줄이는 방향이다.
- 감수한 점: 휴리스틱이 실제 비용을 과대평가하지 않도록(admissible) 식을 맞춰야 한다.
- 검증 방법: "휴리스틱 알고리즘 변경" 단계의 평균 처리시간 비교.
- 관련 코드 흐름: 휴리스틱 변경 적용.
- 관련 테스트 결과: 측정 자료 휴리스틱 변경 단계.
- 확인 필요: 변경 전(유클리드) 원본 코드는 미보존(주석 흔적·폴더명으로 추정).

---

## 4. 왜 sqrt 제거가 의미 있었는가

- 문제 상황: 휴리스틱은 확장하는 노드마다 반복 호출되므로, 제곱근 비용이 누적된다.
- 선택한 방식: 상대 비교에 제곱근이 꼭 필요하지 않은 경우, 8방향 격자에 맞는 거리 식(덧셈·최솟값·상수 곱)으로 대체한다.
- 대안: 제곱근을 유지.
- 선택 이유: 제곱근은 단일 호출은 싸 보여도 반복 루프에서 누적되면 무시할 수 없다. 격자 이동에 맞는 식으로 바꾸면 제곱근 없이도 정확한 하한을 얻을 수 있어, 정확도와 성능을 함께 챙긴다.
- 감수한 점: 식이 이동 규칙(대각 비용)에 종속된다.
- 검증 방법: 휴리스틱 변경 단계의 평균 처리시간 비교.
- 관련 코드 흐름: 휴리스틱 변경 적용.
- 관련 테스트 결과: 측정 자료 휴리스틱 변경 단계.
- 확인 필요: 없음(현재 코드에 제곱근 없음 확인).

---

## 5. 왜 캐시 지역성을 개선했는가

- 문제 상황: A*는 인접 타일을 반복적으로 접근하는데, 격자 데이터가 메모리에 흩어져 있으면 캐시 미스가 잦다.
- 선택한 방식: Tile/Node 구조체 크기를 줄이고, 결과 격자를 한 덩어리 연속 메모리로 잡은 뒤 행 포인터로 2차원처럼 접근한다.
- 대안: `vector<vector<Tile>>`나 행별 개별 할당.
- 선택 이유: 벡터의 벡터·행별 할당은 행마다 힙이 흩어져 인접 타일 접근 시 캐시 미스가 늘어난다. 연속 배치는 캐시 라인 재사용이 좋아 순회·초기화 비용이 준다. 구조체 크기를 줄이면 한 캐시 라인에 더 많은 타일이 들어간다.
- 감수한 점: 연속 블록을 한 번에 할당·해제해야 하고, 인덱싱을 직접 관리한다.
- 검증 방법: "캐시 히트율 높이기" 단계의 평균 처리시간 비교.
- 관련 코드 흐름: 캐시 지역성 개선 적용.
- 관련 테스트 결과: 측정 자료 캐시 단계.
- 확인 필요: 이전(벡터/행별) 버전 코드는 미보존(폴더명으로 추정).

---

## 6. 왜 switch-case를 방향 오프셋 테이블로 바꿨는가

- 문제 상황: 8방향 탐색에서 방향마다 switch 분기가 반복적으로 발생한다.
- 선택한 방식: 방향 오프셋 배열과 비용 배열을 static으로 두고 인덱스로 참조한다.
- 대안: switch-case 유지.
- 선택 이유: 8방향 분기는 확장 노드마다 반복되므로, 분기 예측 실패·점프를 없애면 누적 효과가 있다. 테이블 참조로 오프셋과 비용을 분기 없이 조회하면 코드도 단순해진다. 가독성과 성능을 함께 챙긴다.
- 감수한 점: 방향과 배열 인덱스의 대응을 정확히 유지해야 한다.
- 검증 방법: "switch_case문 제거" 단계의 평균 처리시간 비교.
- 관련 코드 흐름: switch 제거 적용.
- 관련 테스트 결과: 측정 자료 switch 제거 단계.
- 확인 필요: A*의 이전 switch 버전은 미보존이나, BFS용 `Search`에 switch가 남아 있어 같은 파일에서 대조 가능.

## 7. 왜 알고리즘 최적화에서 메모리 배치까지 봤는가

- 문제 상황: 같은 A*라도 실제 처리 시간은 알고리즘 복잡도만으로 설명되지 않았다.
- 선택한 방식: 휴리스틱(탐색량·계산 비용)뿐 아니라 캐시 지역성(메모리 배치)과 분기(switch 제거)까지 단계별로 측정·개선한다.
- 대안: 알고리즘 상수만 보고 최적화.
- 선택 이유: Big-O가 같아도 실제 성능은 메모리 접근 패턴, 캐시 지역성, 분기, 구조체 크기에 영향을 받는다. 단계별 측정으로 이 요소들이 실측 성능을 좌우함을 확인했다. 게임 서버는 많은 객체·좌표·경로를 반복 처리하므로 이런 실제 비용이 중요하다.
- 감수한 점: 각 단계를 측정·비교하는 데 시간이 든다.
- 검증 방법: 단계별 평균 처리시간 비교(280.4μs → 195.9μs).
- 관련 코드 흐름: 휴리스틱/캐시/switch 개선, 측정.
- 관련 테스트 결과: `docs/Test_Report.md`.
- 확인 필요: 없음(단계별 측정 결과로 확인).

## 8. 효과가 없어 되돌린 시도 — open list 객체 위치 변경

- 문제 상황: open list를 멤버 변수에서 지역 변수로 바꾸면 접근 비용이 줄어들 것으로 예상했다.
- 시도한 방식: open list 객체를 함수 지역으로 이동해 측정.
- 결과: 오히려 소폭 나빠져 원복했다.
- 원인 분석: 접근 대상이 open list의 멤버 변수가 아니라 멤버 함수 호출이다. 멤버 객체든 지역 객체든 함수 호출 시 객체 주소를 얻는 비용은 같고, 지역 객체는 호출마다 생성 비용이 추가된다.
- 배운 점: 최적화 아이디어는 적용 전 가설이 맞는지 접근 패턴 수준에서 따져야 하고, 적용 후에는 반드시 측정으로 확인해야 한다. 효과가 없거나 악화되면 되돌린다.
